# 肯德基優惠券哪張划算

**→ https://ahoga000.github.io/kfc-coupon-solver/**

點兩下（想吃什麼 + 價格帶），列出**該價格帶裡最便宜的 3 張優惠券**。不疊券——每一筆就是單獨
一張券，拿代碼去點就好。

本站與台灣肯德基／Yum! Brands 無任何關聯，未取得授權，也不是官方服務。

```
想吃什麼   [堡] [炸雞] [蛋撻] [飲料]              ← 可複選，「或」的關係
價格帶     [$100以下] [$101~150] [$151~200] [$201以上]   ← 單選，互不重疊
```

按下去就直接出結果，不用再按一次「找」。四個按鈕以外的東西可以展開「其他」自己打字
（「蛋塔」也會對到「蛋撻」）。

複選時是**聯集**：含「堡或炸雞」的券排在同一張榜上依總價排，每張卡片標它是因為哪一類上榜。

肯德基的券多到找券本身就是麻煩事。已經有人把「列出所有券 + 搜尋」做得很好了
（[KCouper](https://github.com/Winedays/KCouper)，每天自動更新），但沒有人回答
「我一個人想吃炸雞，該點哪張券」。這個工具只做後者。

## 怎麼跑

需要 Python 3.10（抓資料）與 Node（只有跑測試才需要）。

```bash
# 第一次
py -3.10 -u scripts/collect_seeds.py           # 從公開的優惠券整理網頁撈候選 5 碼代碼
py -3.10 -u scripts/fetch_menu_categories.py   # 單品的菜單分類（11 次請求）
npm run refresh                                 # 打官方 API 驗證 + 正規化（約 25 分鐘）

# 之後只要更新券資料
npm run refresh

# 開來用
npm run serve      # -> http://localhost:8731/
```

手機要連同一台電腦看的話用 `http://<電腦的區網 IP>:8731/`。`serve` 一定要帶 `--bind 0.0.0.0`
—— 不帶的話 Python 在 Windows 上會挑到 IPv6 (`::`)，而 Windows 的 IPv6 socket 預設
`IPV6_V6ONLY=1`，結果是**本機用 localhost 看起來一切正常，手機卻完全連不上**。

`web/` 是自成一包的靜態網站，可以直接丟到任何靜態主機。

**改完前端記得 ctrl+shift+r 硬重載**，`http.server` 的快取會讓你看到舊版還以為沒生效。

## 部署與每日更新

`web/` 是自成一包的靜態網站，丟 GitHub Pages 就能跑（`.github/workflows/pages.yml`，
只發布 `web/`，scraper 與原始資料不進網站）。

每日更新在 `.github/workflows/daily-refresh.yml`：台灣時間 **每天 00:30** 跑一次。

```
抓資料 → 正規化成候選檔 → 閘門檢查 → 通過才覆蓋 web/solver_data.json → commit
```

平日只驗「已知有效」的那批（約 440 個代碼），**週五做全掃**。
因為 `data/invalid_codes.txt` 會讓已標記無效的代碼被跳過 —— 新上架的券如果剛好用到
以前無效的代碼，不全掃就永遠撿不到。全掃日也會順便重跑 `collect_seeds.py` 補新代碼。

### 第一次推上 GitHub 會踩的兩個坑

先決條件：`Settings` → `Pages` → Source 要選 **GitHub Actions**（我們的 workflow 沒帶
自動啟用參數），`Settings` → `Actions` → Workflow permissions 要是 **Read and write**
（每日更新那支要把新資料 commit 回 repo）。然後：

1. **建立分支的那次 push，GitHub 不套用 path filter。** `pages.yml` 設定成只有 `web/**`
   有變動才跑，所以 repo 首推時它一個 run 都不會產生 —— 網站生不出來。
2. **只有 `schedule` / `workflow_dispatch` 的 workflow，首推後不會被登記。**
   Actions 清單裡看不到，連 `Run workflow` 按鈕都沒有，等於排程永遠不會跑。

兩個都靠「動到那個檔案再 push 一次」解決。症狀很容易被誤判成「Actions 被關掉了」，
用公開 API 就能分辨：`/actions/workflows` 回 0、但 `github.com/<owner>/<repo>/actions`
回 200 就代表 Actions 是開著的（被關掉時那頁是 404）。

### 出問題時會怎樣（這是重點）

四種失效模式，處理方式不一樣：

| 失效模式 | 怎麼處理 |
|---|---|
| 門市關閉／店號失效 | **自動換備援門市**。實測過三間不同縣市的店抓到的券完全相同，換店不會改變使用者看到的內容。清單在 `kfc_api.py` 的 `FALLBACK_SHOP_CODES` |
| `orderType` 失效 | 自動換 `3`。（`1` 是外送，實測一張券都拿不到，別用） |
| **IP 被擋（403/429）** | 換門市救不了。直接中止本次抓取 → 閘門不放行 → **保留舊資料**，網站照常運作 |
| API 改格式／抓到一半斷掉 | 同上，閘門擋下來 |

**主防線是閘門不是備援門市。** `scripts/publish_guard.py` 在覆蓋正式檔前檢查：

- 券數不得低於 150 張，也不得低於現行的 70%（抓到一半斷掉就是這樣被擋的）
- **券價兩條獨立路徑必須零不一致**（解析邏輯跟資料對不上就是這裡爆）
- 抓得到原價的比例不得低於 80%
- 今天還有效的券要夠多、`fetched_at` 要是今天或昨天

任何一條不過就 exit 1，正式檔原封不動，Actions 顯示紅燈。使用者那邊只會看到資料日期
停在前一天 —— 網站不會壞，也不會拿到半殘的資料。

前端在資料超過 2 天沒更新時會跳明顯警示（正常每天更新，隔 2 天代表有一次失敗了）。

### 備援門市怎麼來的

`scripts/probe_shops.py` 掃 `QueryDeliveryShops` 找出有效店號，結果存 `data/shops.json`。
掃 TWI100–160 就找到 43 間、橫跨 13 個縣市。這是一次性的調查腳本，不進每日流程。

```bash
py -3.10 -u scripts/probe_shops.py --lo 100 --hi 160   # 掃店號
py -3.10 -u scripts/probe_shops.py --compare           # 驗換門市/換 orderType 有沒有差
```

## 排行怎麼算

1. 關鍵字 → 品項集合（比對品名，以及肯德基自己的分類：炸雞／蛋撻／漢堡／飲料／配餐／主餐／烤雞）
2. 濾掉今天不在效期內、或時段不符的券
3. 每張券挑出「含該品項且**總價最低**」的口味組合
   ——換口味的加價會算進去，`2入原味蛋撻超極酥` 這種一份含多個的份數也會算對
4. 濾掉不在價格帶內的（比的是**實付金額**，不是券的底價）
5. 內容相同的券合併，只留總價最低的，其餘變成「備用代碼」
6. 依**總價**由低到高排；同價時份數多的優先，再同則折扣率高的優先

### 為什麼排總價不排每份單價

一開始排的是每份單價，結果前三名全是多人份大套餐——炸雞第一名是 $233 的 5 塊裝、
第二名 $369 的 7 塊裝。每份單價本來就獎勵大包裝，但一個人點餐時真正的決策數字是總價。
改成排總價之後前三名變成 $54 / $77 / $78，全是 1 份主食的單人餐。

每份單價還是有標在卡片上，可以順便看划不划算——單價特別低的通常就是多人份大包裝。

### 價格帶為什麼要互斥

一開始做成「$100 以下 / $150 以下 / $200 以下 / $200 以上」，結果前三段**永遠給同一批券**
——排序本來就是總價升冪，最便宜的那幾張同時滿足三個上限，按了跟沒按一樣。
改成互不重疊的 `≤100 / 101~150 / 151~200 / ≥201` 之後，每一段才真的是不同的券
（實測四個關鍵字 × 四段共 16 個組合都有結果，且同一張券不會出現在兩段裡）。

### 為什麼不用「幾人份」當篩選

主食份數其實是比價格更乾淨的份量訊號（主食 1 份的券中位數 $125）。
**但不能拿來篩** —— 420 張券裡有 99 張主食 0 份（蛋撻／飲料／點心類），
用主食份數篩會把搜「蛋撻」的結果整批殺光。價格沒有這個問題，而且 $200 以內佔 64%。

### 分類只採用券裡的 slot Title

單品菜單也有分類，但那是「點心/飲料」這種合併大類，拿來做關鍵字比對會把炸雞、
薯條、雞塊全算成飲料（實測搜「飲料」會對到 53 個品項，其中一堆不是飲料）。
改成只用券裡的 slot Title（炸雞／蛋撻／漢堡／飲料／配餐／主餐／烤雞／其他）之後降到 26 個。

辣度變體共用分類——券寫「咔啦脆雞(辣)」、菜單寫「咔啦脆雞」，不共用的話後者會漏掉。

沒出現在任何券裡的品項本來就影響不了排行（排行是在券上跑的），這些品項仍可用品名搜到。

### 為什麼要合併內容相同的券

436 張券只有 337 種內容：**167 張（38%）與別張內容相同，其中 71 張連價格都一樣**。
例如「飲料 ×2 經典冰奶茶」有 7 張不同代碼的券。不合併的話 Top 3 會是同一個優惠的三個代碼。
合併後反而多一個好處：店家不收某張時，卡片上就有可以換的代碼。

## 資料從哪來

台灣肯德基線上訂餐的 API（`olo-api.kfcclub.com.tw`），不需要登入：

| Endpoint | 用途 |
|---|---|
| `/customer/v1/getEVoucherAPI` | 代碼 → 商品碼 |
| `/customer/v1/checkCouponProduct` | 各餐期是否可兌換 |
| `/menu/v1/GetQueryFoodDetail` | 券的內容、價格、效期 |
| `/menu/v1/GetQueryMenu` + `GetQueryFood` | 單品原價 |

這是逆向出來的非公開 API，格式隨時可能改。抓取有 sleep 與退避重試。

**代碼來源採種子清單制**，不做 10^5 全量枚舉——那是對別人的伺服器不厚道，
代價是券庫覆蓋率會比全掃的專案低。想擴大就往 `data/seed_codes.txt` 加代碼，
無效的會被 API 自動淘汰。

## 券價與原價

**券價**由公式算出：

```
券底價 = Original_Price + Σ_slot (預設選項 MListPrice × 份數)
換口味 = 該選項的 AddPrice × 份數        (預設選項的 AddPrice 恆為 0)
```

同一張券的價格有**兩條獨立路徑**：上面的公式，以及官方文案 `Intro` 裡的
「=NT$499元(原價$813)」。每次建檔都對帳，不一致會列進稽核報告。
目前 436 張券：423 張一致、13 張文案沒寫價格、**0 張不一致**。
這個機制實際抓到過三個解析 bug，值得留著。

**原價只採用官方文案**，寫法有三種：`原價$813`、`最高價值$240元`、`市價NT$144`，
另有一種是 `(省NT$38元)` → 原價 = 券價 + 省。目前覆蓋 422/436（96%），
其餘顯示「原價未提供」。

⚠️ **原價不可以自己算**。試過用「單品價 × 份數」加總，`8塊上校雞塊+飲料` 官方寫原價 $133，
算出來是 **$569**——因為 `上校雞塊` 的單價被配到 `點心盒-上校雞塊+香酥脆薯(小) $67` 這個
含薯條的點心盒。這種錯不報錯，只會把折扣率默默灌水。`match_price()` 現在會擋掉
組合盒、多件包裝、組合餐，寧可查不到價也不猜。

## 已知限制

- **門市**：主用台北雙連（`TWI104`）。**實測過台南／台北／板橋三間店、四張券，
  價格與內容一字不差**，所以券這一層各店是一樣的（單品原價那支 API 本來就沒帶店號）。
  但這是抽樣，不是全面驗證。
- **餐期**：資料裡只分得出「早餐（餐期 1）」與「早餐以外（餐期 2-5）」。
  這是從 436 張券的分佈推出來的不是猜的——只有餐期 1 的 16 張清一色是燒餅／薯餅／粥／蛋堡，
  不含餐期 1 的 408 張沒有一張提到早餐（見 `web/app.js` 註解）。
- **不會出現過期的券**：抓取時拿當天日期問過 API，前端每次載入又用當天日期濾一次。
  但反方向會：新出的券要重跑 `npm run refresh` 才會進來，資料超過 3 天前端會提醒。
- **品名比對**：`data/taxonomy_audit.txt` 會列出哪些單價是用包含關係猜的、哪些查不到價。
- 僅供個人使用。

## 湊單最佳化（保留但 UI 沒有露出）

`web/optimizer.js` 裡的 `solve()` / `solveWithAlternatives()` 可以算出**跨多張券**的最省組合
（整數覆蓋問題，需求向量上的 DP，單點當虛擬券）。功能完整、有 24 個測試含一支
**獨立的暴力窮舉 oracle**，但 UI 沒有接——多張券一起用在實際點餐時體驗未確認。
確認可行的話接回來即可，不用重寫。
